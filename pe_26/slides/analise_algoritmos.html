Analisando algoritmos

Comparando soluções para palíndromo

No lab, vimos dois modos de testar se uma lista ligada é um palíndromo.

  1. Algoritmo análogo ao de vetores;
  2. Algoritmo usando inversão da lista como sub-rotina.

Como decidir qual solução usar?

  • Correção: O algoritmo funciona para qualquer entrada válida?
  • Eficiência: Quanto tempo o algoritmo leva? Quanta memória extra ele usa?

Correção e invariantes

Revisitando busca em um vetor

Entrada: Vetor v com n elementos e um inteiro x

Saida: O índice de uma ocorrência de x, ou -1 caso não haja nenhuma.

int busca(int v[], int n, int x) {
    int i = 0;

    while (/* A */ i < n && v[i] != x)
        i++;
    
    if (i == n)
        return -1;
    return i;
}

O que sabemos sobre os elementos em v[0..i-1] chegar ao ponto A?

Nenhum deles é igual a x.

Invariantes

Um invariante de laço é uma afirmação que é verdadeira no início

Invariantes servem alguns propósitos:

  • Checar precisamente a corretude de um algoritmo;
  • Auxiliar na depuração de implementações;
  • As vezes nos ajudam a enxergar implementações mais eficientes;

Como verificar um invariante?

int i = 0;
while (/* A */ i < n && v[i] != x)
    i++;

Invariante: Nenhum elemento em v[0..i-1] é igual a x.

  • Inicialização: Vale antes da primeira avaliação da condição?
  • Manutenção: Se vale antes de uma iteração, continua valendo depois dela?

Usando o invariante

int i = 0;
while (/* A */ i < n && v[i] != x)
    i++;
if (i == n)
    return -1;
return i;

Ao sair do laço, sabemos que nenhum elemento em v[0..i-1] é igual a x.

  • Se i == n, então x não aparece no vetor;
  • Caso contrário, v[i] == x (condição de saída do laço).

E se o laço nunca terminar?

int i = 0;
while (/* A */ i < n && v[i] != x) {
    // Esquecemos de incrementar i
}

Nosso invariante continua valendo!

Para mostrar que um algoritmo está correto, queremos mostrar que:

  • Se terminar, retorna o resultado desejado;
  • O algoritmo termina para toda entrada válida.

Na busca correta, i aumenta a cada iteração e não ultrapassa n.

Exemplo: palíndromo

int eh_palindromo(int v[], int n) {
    int esq = 0, dir = n - 1;
    
    while (/* A */ esq < dir) {
        if (v[esq] != v[dir])
            return 0;
        esq++; dir--;
    }
    return 1;
}

O que sabemos toda vez que chegamos ao ponto A?

Invariante: esq + dir == n - 1 e v[0..esq-1] == v[dir+1..n-1].

  • Essa invariante vale na inicialização? Temos manutenção dela?

  • Por que esse invariante nos permite retornar 1 quando esq >= dir?

Exemplo: elementos repetidos em um vetor

Entrada: Vetor v com n

Saida: Retornamos 1 se existirem posições distintas em v com mesmo valor, 0 caso contrário.

int tem_repetidos(int v[], int n) {
    for (int i = 0; i < n; i++) {
        for (int j = i + 1; j < n; j++) {
            if (v[i] == v[j])
                return 1;
        }
    }
    return 0;
}

Pergunta: Por que começamos com j = i + 1?

Invariantes de laços aninhados

int tem_repetidos(int v[], int n) {
    for (int i = 0; /* A */ i < n; i++) {
        for (int j = i + 1; /* B */ j < n; j++) {
            if (v[i] == v[j])
                return 1;
        }
    }
    return 0;
}

O que sabemos sobre o vetor ao chegar aos pontos A e B?

Invariantes de laços aninhados

int tem_repetidos(int v[], int n) {
    for (int i = 0; /* A */ i < n; i++) {
        for (int j = i + 1; /* B */ j < n; j++) {
            if (v[i] == v[j])
                return 1;
        }
    }
    return 0;
}

Invariante B (interno): v[i] é diferente dos elementos em v[i+1 .. j-1].

Invariante A (externo): Se k < i, v[k] != v[j] para todo j > k

Como os invariantes se relacionam?

B: v[i] é diferente dos elementos em v[i+1 .. j-1].

A: Se k < i, v[k] != v[j] para todo j > k

Quando o laço interno termina (j == n):

  • B implica que v[i] != v[k] para todo k > i.
  • Logo, podemos incrementar i preservando A!

Assim:

  • Se retornamos 1, encontramos uma repetição.
  • Se chegamos ao return 0 (i == n ao sair do laço), o invariante A garante que não há repetição.

Análise de tempo

Como medir o tempo de um algoritmo?

Podemos executar o programa (diversas vezes) e medir seu tempo de execução.

Pode depender de vários fatores:

  • O computador em que executamos o programa;
  • O compilador;
  • A entrada que damos para o programa.

Outra ideia: contar o número de operações realizadas em função do tamanho da entrada.

Quanto trabalho a busca realiza?

int busca(int v[], int n, int x) {
    int i = 0;
    while (i < n && v[i] != x)
        i++;
    if (i == n)
        return -1;
    return i;
}

Pergunta: Quantas vezes cada instrução é executada?

Vamos supor que cada uma das demais instruções do corpo da função tem custo constante.

Assumir isso é razoável?

O tempo depende da entrada

Para o mesmo valor de n, podemos ter tempos de execução diferentes!

  • Melhor caso: encontramos x logo na primeira posição.
  • Pior caso: x não está no vetor (por exemplo).

No nosso modelo de contagem, no pior caso temos

\[T(n) = 2n + 4.\]

O tempo de pior caso cresce linearmente com n.

E para encontrar elementos repetidos?

int tem_repetidos(int v[], int n) {
    for (int i = 0; i < n; i++) {
        for (int j = i + 1; j < n; j++) {
            if (v[i] == v[j])
                return 1;
        }
    }
    return 0;
}

Quantas comparações entre elementos fazemos no pior caso?

Tempo quadrático

No pior caso, fazemos

\[ (n-1)+(n-2)+\cdots+1 = \frac{n(n-1)}{2} \]

comparações entre elementos do vetor.

O número de comparações cresce quadraticamente com n.

As demais operações não mudam essa ordem de crescimento.

Comparando ordens de crescimento

\(n\) Busca: \(2n+4\) Repetidos: \(n(n-1)/2\)
10 24 45
100 204 4.950
1.000 2.004 499.500
10.000 20.004 49.995.000

O que acontece quando dobramos o tamanho da entrada?

  • Um custo linear aproximadamente dobra;
  • Um custo quadrático aproximadamente quadruplica.

Notação \(O\) (Big-Oh notation)

Em vez de nos preocuparmos com a contagem exata, discutimos o tempo de execução baseado na ordem de grandeza do seu crescimento:

  • Busca sequencial leva tempo em \(O(n)\)
  • O algoritmo para elementos repetido leva tempo em \(O(n^2)\).

Dizemos que \(T(n)=O(f(n))\) se existem constantes \(c>0\) e \(n_0\) tais que

\[T(n)\leq c\,f(n),\qquad\text{para todo }n\geq n_0.\]

Interpretação: Para entradas suficientemente grandes, o custo cresce no máximo proporcionalmente a \(f(n)\).

Alguns exemplos

  • \(2n+4=O(n)\);
  • \(\dfrac{n(n-1)}{2}=O(n^2)\);
  • \(3n^2+5n+10=O(n^2)\);
  • \(15=O(1)\).

Pergunta: É correto dizer que \(2n+4=O(n^2)\)?

Sim! Mas normalmente queremos dar um limite superior tão preciso quanto possível.

Busca binária

Podemos fazer melhor?

Podemos fazer busca de forma mais rápida que o algoritmo a baixo?

int busca(int v[], int n, int x) {
    int i = 0;
    while (i < n && v[i] != x)
        i++;
    if (i == n)
        return -1;
    return i;
}

Não: no pior caso precisamos examinar todos os elementos para saber se x está nele.

E se o vetor estiver ordenado?

Buscando em um vetor ordenado

Queremos encontrar x = 38 no seguinte vetor:

0 1 2 3 4 5 6 7 8
2 5 8 12 17 23 38 41 56

E se começarmos a busca pelo elemento do meio (v[4])?

Como v[4] < x, sabemos que x não aparece nas posições 0, ..., 4.

Basta procurar no restante do vetor!

Busca binária: repetindo a ideia

0 1 2 3 4 5 6 7 8
2 5 8 12 17 23 38 41 56

Agora buscamos apenas entre as posições 5 e 8.

Se compararmos x com v[6], encontramos o elemento!

A cada iteração - ou encontramos o elemento; - ou descartamos pelo menos metade dos candidatos.

Como delimitar o trecho de busca?

Vamos guardar os índices esq e dir, que delimitam o trecho que ainda precisamos examinar (incluindo as duas extremidades).

Invariante: v[0..esq-1] < x e v[dir+1..n-1] > x.

Inicialmente: esq = 0 e dir = n - 1.

Se esq > dir, o que podemos concluir?

Como diminuir o trecho de busca?

Seja meio o índice do elemento no meio do trecho:

int meio = esq + (dir - esq) / 2;
  • Se v[meio] == x, encontramos o elemento;
  • Se v[meio] < x, podemos descartar meio e todos os elementos anteriores a ele;
  • Se v[meio] > x, podemos descartar meio e todos os elementos posteriores a ele.

Como devemos atualizar esq e dir em cada caso?

Busca binária (código)

// Supõe que v está ordenado em ordem não decrescente.
int busca_binaria(int v[], int n, int x) {
    int esq = 0, dir = n - 1;
    while (/* A */ esq <= dir) {
        int meio = esq + (dir - esq) / 2;
        if (v[meio] == x)
            return meio;
        if (v[meio] < x)
            esq = meio + 1;
        else
            dir = meio - 1;
    }
    return -1;
}

Invariante em A: v[0..esq-1] < x e v[dir+1..n-1] > x

Vale inicialmente? Manutenção? O que sabemos ao chegar ao return -1?

E por que o algoritmo termina?

if (v[meio] < x)
    esq = meio + 1;
else
    dir = meio - 1;

A cada iteração em que não encontramos x, diminuímos estritamente o tamanho do trecho de busca (dir - esq + 1).

Pergunta: O que poderia acontecer se tivéssemos escrito esq = meio em vez de esq = meio + 1?

Quanto trabalho a busca binária realiza?

int busca_binaria(int v[], int n, int x) {
    int esq = 0, dir = n - 1;
    while (esq <= dir) {
        int meio = esq + (dir - esq) / 2;
        if (v[meio] == x)
            return meio;
        if (v[meio] < x)
            esq = meio + 1;
        else
            dir = meio - 1;
    }
    return -1;
}

Quanto trabalho fazemos em cada iteração? E quantas iterações podemos ter?

O número de iterações

Inicialmente, temos n candidatos.

A cada iteração que não encontra x, restam no máximo metade dos candidatos.

Após \(k\) iterações, o número de candidatos é no máximo

\[\frac{n}{2^k}.\]

Para garantir que não reste nenhum candidato, basta garantir que

\[\frac{n}{2^k}<1,\qquad\text{ou seja,}\qquad k>\log_2 n.\]

Tempo logarítmico

Para \(n\geq 1\), fazemos no máximo \(\lfloor\log_2 n\rfloor+1\) iterações.

Como cada iteração leva tempo \(O(1)\), a busca binária leva tempo em \(O(\log n)\) no pior caso.

\(n\) Busca sequencial (máx.) Busca binária (máx.)
100 100 7
1.000 1.000 10
1.000.000 1.000.000 20
1.000.000.000 1.000.000.000 30

A tabela compara o número de iterações, não o tempo exato de execução.

Além da notação \(O\)

Qual algoritmo é mais rápido?

Suponha que temos dois algoritmos para resolver um mesmo problema:

  • Algoritmo A: \(T_A(n)=1000n\) (tempo \(O(n)\));
  • Algoritmo B: \(T_B(n)=n^2\) (tempo \(O(n^2)\)).
\(n\) Algoritmo A Algoritmo B
10 10.000 100
100 100.000 10.000
1.000 1.000.000 1.000.000
10.000 10.000.000 100.000.000

As constantes também importam!

O modelo de análise também importa

Percorrer um vetor e percorrer uma lista ligada têm ambos tempo \(O(n)\).

Mas os elementos de um vetor estão em posições consecutivas da memória, enquanto os nós de uma lista podem estar espalhados.

Isso pode fazer bastante diferença no tempo de execução (cache do processador).

Outras coisas que podemos querer analisar:

  • A quantidade de memória utilizada;
  • O tempo de execução em entradas típicas (não apenas no pior caso).

Algumas perguntas

  • A busca binária levaria tempo \(O(\log n)\) em uma lista ligada ordenada?
  • Se temos um vetor não ordenado e queremos fazer uma única busca, vale a pena ordenar o vetor (tempo \(O(n \log n)\)) para fazer busca binária?
  • E se quisermos fazer milhares de buscas no mesmo vetor?

Algoritmos galácticos

Suponha agora que

\[T_A(n)=10^{100}n,\qquad T_B(n)=n^2.\]

O algoritmo A é assintoticamente melhor, mas só será mais rápido para \(n>10^{100}\)!

Chamamos informalmente de algoritmos galácticos algoritmos cujas vantagens assintóticas só aparecem para tamanhos de entrada enormes, sem relevância prática conhecida.

Um exemplo de algoritmo galático recente: ETH

A Exponential Time Hypothesis (ETH) era uma conjectura famosa de que o problema 3-SAT com \(n\) variáveis não poderia ser resolvido em tempo melhor que \(O(2^n)\) no pior caso.

Em outubro de 2026, trabalhos da OpenAI e da Anthropic anunciaram algoritmos de tempo subexponencial para 3-SAT que refutam ETH!!

Curiosamente, os algoritmos só fazer algo interessante para entradas gigantes. Quote de um blog post do Ben Recht:

The derived algorithm runs exhaustive search—the algorithm Edmonds declared bad in 1965—if the number of variables is less than \(10^{10,000,000,000,000,000,000,000,000}\).

O número de atomos no universo é “só” \(\approx 10^{80}\) 😛.

Pequeno resumo

  • Invariantes nos ajudam a raciocinar sobre a correção de um algoritmo;
  • Análise assintótica nos ajuda a entender como seu custo cresce com o tamanho da entrada;
  • Propriedades da entrada (por exemplo, um vetor estar ordenado) podem nos permitir construir algoritmos melhores.
